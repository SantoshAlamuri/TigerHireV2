It solves a problem that every recruiter and job seeker in India experiences daily: the signal is out there — companies are hiring, people are available — but the two sides never connect efficiently. Traditional platforms require manual effort from both sides, produce stale results, and charge for access to data that is often outdated and poorly matched. Problem Statement 2.1 The Recruiter's Reality A recruiter at an Indian startup today opens LinkedIn Recruiter (₹80,000–₹2,00,000/month), runs keyword searches, filters through hundreds of profiles that are months old, sends 50 InMails, hears back from 4, and spends the next 3 hours scheduling calls. This is the industry standard. The tools are expensive, the data is stale, and the matching is entirely manual.  2.2 The Job Seeker's Reality A senior professional ready to move sends their résumé to 30 companies, never hears back from 25, receives generic rejections from 4, and — if they're lucky — gets one callback that turns out to be for a completely different role than advertised. They have no visibility into how their profile ranks, no feedback on what's missing, and no intelligence on which companies are actively hiring for their skill set.  2.3 Why Existing Platforms Fail Platform Failure for Companies Failure for Candidates Core Missing Piece LinkedIn Recruiter Expensive; mostly passive candidates; response rates <15% InMails ignored; profile buried; no ranking feedback Real-time intent + fit scoring Naukri / Monster Stale databases; poor signal quality; lots of noise Spam from irrelevant recruiters; zero transparency Freshness signals + intelligent matching Indeed India High volume, low quality; no matching intelligence Faceless applications; never know where you stand Candidate scoring + recruiter feedback loop ATS (Greenhouse, Lever) Only manages inbound; no proactive sourcing Résumé submitted = black hole Outbound sourcing + scoring layer TalentPulse ✓ Real-time signals, FitScore shortlists, both sides verified ✓ Ranked visibility, fit feedback, proactive matching This is what we build  2.4 The FitScore Gap The most critical missing piece across all existing platforms is objective, explainable fit scoring. Recruiters screen résumés subjectively, inconsistently, and slowly. A single senior hire involves reviewing 80–200 résumés, taking 6–10 hours of recruiter time. FitScore reduces this to minutes — and makes the scoring auditable, consistent, and bias-reduced. No platform in India does this well today. 3. Product Architecture — Three-Agent System 3.1 System Overview TalentPulse is built on a three-agent architecture where each agent owns a distinct domain but all three share a common data layer and communicate via Supabase Realtime and internal API events. The system is designed to be fully serverless, horizontally scalable, and deployable on Vercel with zero infrastructure management overhead.  Architecture Layers Layer 1 — Ingestion:    Apify actors + custom crawlers → raw signals scraped on scheduled cadence Layer 2 — Processing:   Claude API (claude-sonnet-4-6) → enrichment, classification, scoring Layer 3 — Storage:      Supabase (PostgreSQL) → structured data  |  pgvector → semantic search Layer 4 — Orchestration: Supabase Edge Functions + cron jobs → agent coordination Layer 5 — API:          Next.js API routes (Vercel) → all client-facing endpoints Layer 6 — Frontend:     Next.js App Router → recruiter dashboard, candidate dashboard, admin Layer 7 — Payments:     Stripe → subscription billing for both sides Layer 8 — Comms:        Resend (email) + WhatsApp Business API → notifications both sides  3.2 Agent Communication Model Agents do not call each other directly. They publish events to a Supabase Realtime channel, and each agent subscribes to events from the others. This loose coupling means any agent can be upgraded, redeployed, or scaled independently without affecting the others. Agent 1 — Talent Scout Agent 4.1 Purpose The Talent Scout Agent is the supply-side engine of TalentPulse. Its job is to find people who are open to work before they have submitted a single application — and to build the richest possible profile of each person using only public data. This is the core supply-side moat: a continuously refreshed, AI-enriched pool of genuinely available talent.  4.2 Signal Sources & Detection Logic Source Signal Type Detection Method Freshness Window Est. The pipeline runs as a Supabase Edge Function triggered by a new row insertion in the raw_signals table.  Enrichment Pipeline Steps Step 1 — Parse:       Extract name (if public), current role, company, location, years of experience from raw signal text Step 2 — Normalise:   Standardise role title to canonical taxonomy (e.g. 'SDE-2' → 'Software Engineer L2') Step 3 — Classify:    Assign function (Engineering / Product / Design / Sales / HR / Finance / Operations) Step 4 — Seniority:   Map to level (Intern / Junior / Mid / Senior / Lead / Manager / Director / VP / C-Suite) Step 5 — Skills:      Extract inferred skills from profile text; tag as [verified] vs [inferred] Step 6 — Location:    Geocode to city + state; detect remote-only preference if stated Step 7 — Salary:      Infer expected salary range from role + seniority + location using market data Step 8 — Intent Score: Score 0–100: 100 = explicitly active seeker today; 1 = very weak passive signal Step 9 — Dedupe:      Cross-reference against existing profiles using email/phone/name+company hash Step 10 — Quality:    Assign profile completeness score; flag if insufficient data for matching  4.4 Intent Scoring Algorithm The intent score is the most important output of the Talent Scout Agent. It tells recruiters how actively a person is seeking work right now, so they can prioritise outreach accordingly. Agent 3 — FitScore Agent 6.1 Purpose & Philosophy FitScore is the intelligence layer that transforms TalentPulse from a data aggregator into a decision-support platform. Its job is to score every candidate profile against every relevant job description and return a structured, explainable score that a recruiter can act on in seconds.  The philosophy behind FitScore is explainability over black-box ranking. Every score comes with a dimension-level breakdown, specific strengths, specific gaps, and a plain-English recruiter summary. A recruiter should be able to look at a FitScore card and make a shortlisting decision in under 30 seconds.  6.2 Two Operating Modes Mode Trigger Use Case Output JD → Résumé Scoring Recruiter uploads or selects a JD; platform scores entire candidate pool against it Company has a live role and wants a ranked shortlist from TalentPulse's pool Ranked list of candidates with FitScore 0–100; top 10 highlighted Résumé → JD Matching Candidate registers or signal is detected; platform scores their profile against all relevant open JDs Candidate wants to see which live roles they're best matched for Ranked list of JDs with match %; dimension breakdown per JD; improvement tips Batch Scoring Nightly job — re-score all active candidate-JD pairs where either side has been updated in last 24 hrs Keep scores fresh as JDs are updated and candidate profiles evolve Updated scores in DB; recruiters see freshness timestamp on every score Real-Time Scoring New candidate detected or new JD posted → immediate scoring trigger via Supabase event Recruiter sees a new candidate appear with their score already computed Score ready within 60 seconds of signal detection  6.3 Scoring Dimensions — The FitScore Framework FitScore evaluates every candidate-JD pair across six weighted dimensions. This is a non-trivial NLP problem — JDs are written in wildly inconsistent formats and often contain implicit requirements that are not explicitly stated. The JD parser handles: Explicit required skills vs preferred/nice-to-have skills (different weights in scoring) Hard requirements vs soft requirements (years of experience, degree, certifications) Implicit seniority signals ('you will mentor a team' = senior; 'you will be mentored' = junior) Salary range extraction — even when written in non-standard formats ('6–8 LPA', '₹80K/month', 'competitive') Culture and work style signals ('fast-paced startup' vs 'process-driven enterprise') — used to match candidate self-description Location flexibility signals — 'hybrid', 'remote-first', 'Bengaluru preferred but flexible'  6.6 Résumé / Profile Parser Candidate profiles arrive from two sources: AI-detected signals (partial data) and self-uploaded résumés (rich data). The résumé parser handles: PDF, DOCX, LinkedIn PDF export, plain text résumés Structured extraction: work history (company, role, duration, responsibilities), education, skills, certifications, projects Skill inference: if a candidate lists '5 years at a React company' without mentioning React, it is inferred with a lower confidence tag Career trajectory analysis: promotions, lateral moves, domain switches — used for seniority and ambition scoring Gap detection: employment gaps flagged for recruiter awareness (not penalised in scoring — reported neutrally) ATS format standardisation: output is always stored in canonical schema regardless of résumé format  6.7 Bias Reduction Design FitScore is designed to reduce the subjective biases that plague manual résumé screening. The system enforces several explicit design choices to achieve this: Name, gender, and photo are not inputs to the scoring algorithm — candidates are scored on skills and experience only University name is not a direct scoring input — only degree level and field of study are used Employment gap is reported neutrally, not penalised (recruiter can choose how to weight it) Company prestige heuristics are not used — a 5-year SWE at a Series B startup scores the same as a 5-year SWE at a FAANG company if their skills match All scoring weights are visible and configurable — no black-box ranking Audit log: every score is stored with the model version, prompt version, and input data snapshot — reproducible and auditable 7. Two-Sided Marketplace Model 7.1 Market Dynamics A two-sided marketplace only works when both sides find value. The cold start problem — where neither side joins without the other — is the single biggest risk for any marketplace product. TalentPulse solves this by seeding the supply side (candidates) before any demand side (companies) sees the platform. Companies arrive to a full, scored pool on day one.  Side Value Proposition Why They Stay Primary Monetisation Candidates (Supply) Your profile is proactively matched to live roles. FitScore shows you exactly how you rank and what to fix. Stop applying blindly. Ongoing matches delivered to them; profile improves over time; real feedback loop Premium visibility + Pro subscription Companies (Demand) Receive a ranked, scored shortlist of candidates who are open right now — matched against your exact JD. No posting required. Consistent supply of fresh, scored candidates; ATS integration reduces admin; saves 10+ hrs/hire Subscription tiers + pay-per-unlock  7.2 Network Effects TalentPulse has two compounding network effects that make it harder to replicate over time: More candidates → better matches for companies → more companies join → more companies means more matches for candidates → more candidates self-register. Classic two-sided flywheel. More FitScore data → better scoring model → higher recruiter trust → more companies use it → more JDs in the system → more scoring data. A data moat that grows with usage. 8. The following controls are built into the architecture from day one, not bolted on later:  DPDP Requirement TalentPulse Implementation Lawful basis for processing personal data Legitimate interest (recruitment matching) — documented in Privacy Policy; candidates can opt out at any time via profile toggle Data minimisation Only data necessary for matching is collected; raw scraped text is processed and then discarded; PII stored in minimal form Right to erasure Self-service deletion via candidate dashboard; triggers anonymisation of all PII columns (name, email, phone → hashed); score data retained in anonymised form for model training Data localisation All Supabase infrastructure in ap-south-1 (Mumbai); no personal data leaves Indian AWS region; Vercel edge cache contains no PII Security safeguards All data encrypted at rest (AES-256 via Supabase/AWS); TLS 1.3 in transit; Row Level Security on all tables; no PII in logs Transparency Privacy policy written in plain English and Hindi; candidates shown exactly where their profile was detected and what data is held Consent for self-registered users Explicit opt-in checkbox at registration; consent logged with timestamp, IP hash, and version of privacy policy accepted Data retention Candidate signals: retained 90 days; inactive profiles: anonymised after 12 months of no activity; active profiles: retained while account is active  11.2 Platform Terms of Service Compliance Platform Risk Level Our Approach LinkedIn HIGH Scrape only truly public data (no login required).
